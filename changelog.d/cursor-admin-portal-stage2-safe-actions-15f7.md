## Admin portal Stage 2: audit helper, safe email actions, support queue (branch `cursor/admin-portal-stage2-safe-actions-15f7`) — 2026-08-22

**Trigger**: Stage 1 (PR #142) shipped the double guard and the read-only user list. This stage adds the first *mutating* admin actions, so it also has to answer "how do we log a privileged action once, correctly, every time" before any mutation ships.

`[ADDED]` **`writeAdminAuditLog` — the one writer of `admin_audit_log`.** `apps/web/lib/admin/audit-log.ts` takes an already-constructed service-role client (mirrors `readAdminRow`'s shape, so it stays directly unit- and live-DB-testable without a `server-only` import) and a closed action vocabulary (`resend_confirmation_email`, `resend_password_reset_email`, `close_support_request`, `reopen_support_request`). It throws on anything outside that vocabulary and — critically — throws if the insert itself fails, rather than swallowing the error: an unlogged privileged action is worse than a failed one. Every mutating action below calls it in the same server function as its mutation, never queued or best-effort.

`[ADDED]` **Resend-email action (`POST /api/admin/users/[id]/resend-email`).** Branches on the target's real `email_confirmed_at` (via `auth.admin.getUserById`) rather than sending one generic email: an unconfirmed signup gets `auth.resend({ type: "signup" })` (GoTrue's real resend, unlike `auth.admin.generateLink`, which only mints a link and never emails it — confirmed against the docs before relying on it); a confirmed user gets `auth.resetPasswordForEmail`, the same call `login-form.tsx`'s own "forgot password" flow uses. No `profiles` write of any kind — this only triggers an email. `requireAdminApi()` guards the route itself, independent of the `/admin` layout. Verified live against the real project with one throwaway unconfirmed user and one throwaway confirmed user: both branches resolve correctly and each produces exactly one audit row with the right actor/target/action/`metadata.email_type`.

`[ADDED]` **Support queue.** New `support_requests` table (migration `20260822120000_admin_safe_actions_and_support_queue.sql`, follow-up privilege fix in `20260822130000_support_request_rate_limit_revoke_execute.sql`): authenticated users may INSERT their own row only (`owner_id = auth.uid()`); there is no select/update/delete policy for anon or authenticated at all — not even for the row's own owner — same "no policy = no client access" posture `admin_users` proved for those commands. A BEFORE INSERT trigger caps each owner to 5 inserts per rolling hour (a cheaper stand-in for the `vela_rate_limits` table+RPC pattern, since this insert goes through the plain owner-insert policy from the client's own session rather than a dedicated server route to rate-limit at). `purge_own_account_data()` got an additive edit so a leftover support request can never block self-serve account deletion (the same NO-ACTION-FK class of fix `trial_emails`/`invites` already needed there). The Settings page (`apps/web/app/app/settings/page.tsx`) got a "Contact support" form that inserts directly via the user's own session client — no server route in front of it, so `.select()` is never chained (there's nothing to read back). The admin view (`/admin/support`, `apps/web/app/admin/support/page.tsx`) lists requests open-first via a service-role read, and Close/Reopen are separate guarded routes (`POST /api/admin/support/[id]/{close,reopen}`) that set `status` + `handled_by` + `handled_at` together and then audit — never client-writable directly, and a same-state transition (closing an already-closed request) is rejected as a conflict rather than silently re-stamping the handler. The view only links out to the help@ inbox; no email ingestion is built.

`[DECISION]` **`resend`/`resetPasswordForEmail` over `auth.admin.generateLink`.** `generateLink` is documented to only mint a link and never send it — using it here would have silently shipped a "resend" button that resends nothing. Both calls actually used are public GoTrue endpoints (no admin privilege required to invoke them), run server-side here specifically so an *admin* can trigger them for a user who isn't present to trigger them for themselves.

**Verified**: live against the real project (throwaway accounts/rows, all cleaned up in `afterAll`) — a second authenticated user cannot read the first user's `support_requests` row (permission-denied, not an empty result); a user can insert their own row but cannot read, update, or delete it, and cannot insert on someone else's behalf; the rate-limit trigger fires on the 6th insert within the window; `transitionSupportRequest` sets status/handled_by/handled_at and rejects a same-state transition; every mutating path (resend-email, close, reopen) produces exactly one `admin_audit_log` row with the admin as actor and the affected user as target; each new `/api/admin/**` route independently returns 403 to both a signed-in non-admin session and an anonymous request. `pnpm --filter @galaxia/web typecheck`, the new Vitest suites (unit + live), and a production `next build` all pass.

**After merge**: the migrations (`20260822120000_admin_safe_actions_and_support_queue.sql`, `20260822130000_support_request_rate_limit_revoke_execute.sql`) are **already applied to the live project** (there is no local Supabase stack here — see AGENTS.md — so they were applied directly via the Supabase MCP tool during this stage, the same way the live-DB verification above needed the real table to exist). Nothing further to run against the database. The app half deploys the normal way (Vercel on merge to `main`).
