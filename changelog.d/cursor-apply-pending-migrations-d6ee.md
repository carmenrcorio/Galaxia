## Apply pending migrations and the 60-second timestamp rule (branch `cursor/apply-pending-migrations-d6ee`) — 2026-09-14

**Trigger**: Production `eigfvribtntbxyjutsma` had eight local files that `npx supabase migration list` showed as LOCAL YES / REMOTE NO. Five of those names were already in the ledger under MCP apply-time versions. Two files on `main` share the prefix `20260914270000`, so the CLI cannot mark both REMOTE YES.

`[FIXED]` **Three committed migrations that were not in the production ledger by name are now applied** on `eigfvribtntbxyjutsma`: `comparison_history` (table, owner RLS, purge/delete_own_person deletes), `weekly_constellation_letter` (opt-out column, `constellation_letters` ledger, purge delete), and `create_connect_invite_rate_limit` (10 pending connect invites per 24 hours). SQL ran from the committed files. Ledger names match. File timestamps were written onto those ledger rows so `npx supabase migration list` shows REMOTE YES for `20260914220000` through `20260914260000`.

`[DECISION]` **Five files were already applied by snake_case name** (`notes_vela_pin_theme`, `f12_internal_links`, `f12_stagger_published_at`, `notes_moment_kind`, `people_star_scale_and_free_seat`). Their SQL was not re-run. Re-applying `f12_internal_links` would bump `posts.updated_at` on every published row even when `replace()` is a no-op. Duplicate ledger names fail Migration Ledger Parity. Their MCP apply-time versions were updated to the committed prefixes except the collision below.

`[OPEN]` **`20260914270000_notes_moment_kind.sql` and `20260914270000_people_star_scale_and_free_seat.sql` share one timestamp.** `schema_migrations.version` is a primary key, so only one remote row can hold `20260914270000`. The CLI therefore lists one of those files as LOCAL YES / REMOTE NO and keeps `20260914193248 people_star_scale_and_free_seat` as REMOTE YES / LOCAL NO. Both names remain in the ledger (parity identity). This branch does not rename or edit migration files. A later rename of one file to a timestamp at least 60 seconds after the current max would close the leftover.

`[ADDED]` **TIMESTAMP RULE** in `ENGINEERING.md` §16, with a one-line pointer at the top of `AGENTS.md`. Before creating any migration file, run `npx supabase migration list` and take a prefix at least 60 seconds after the highest existing timestamp. Never create two migrations within 60 seconds.

`[NOTE]` **No pending file contained `CREATE INDEX CONCURRENTLY`.** Mentions in comments are the forbidden form, not statements. Security advisors after apply: `constellation_letters` `rls_enabled_no_policy` INFO (service-role only, same as `daily_nudge_emails` / `trial_emails`). `create_connect_invite` remains an intentional authenticated SECURITY DEFINER RPC.
