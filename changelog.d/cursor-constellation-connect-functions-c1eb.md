## Constellation Connect: the transactional core (branch `cursor/constellation-connect-functions-c1eb`) - 2026-09-13

**Trigger**: `design/galaxia-constellation-connect-plan.md` (PR #213) was approved through the schema layer (PR #217, `20260913160000_constellation_connect_schema.sql`). This builds the nine SECURITY DEFINER RPC functions the plan's section 3 describes on top of that schema. RPCs only: no routes, no UI, callable from either client with `supabase.rpc()`.

`[OPEN]` `design/galaxia-constellation-connect-plan.md` section 11's build-order table says "the eight RPCs," but its own section 3 gives a full signature or behavior for nine distinct functions (`create_connect_invite`, `revoke_connect_invite`, `connect_invite_preview`, `accept_connect_invite`, `add_sender_to_constellation`, `set_connection_share_level`, `revoke_connection`, `approve_reverse_grant`, `acknowledge_connect_accept`), each with a real caller elsewhere in the plan. Implemented all nine; treating "eight" as a miscount in the same family as the plan's own already-corrected `GALAXY_RELATION_PICKER_OPTIONS` count and the unsatisfiable `invites_accept_fields_together` CHECK (both fixed in the schema migration's changelog fragment).

`[ADDED]` **`supabase/migrations/20260913170000_constellation_connect_schema_completion.sql`.** The four pieces PR #217's own changelog fragment deliberately deferred because only the functions in this branch consume them: the `invites` indexes (`invites_from_user_status_idx`, the partial unique `invites_one_pending_connect_per_person` that makes regenerate safe, `invites_connect_unacked_idx`), `people_linked_user_idx`, the `people_linked_chart_requires_link` CHECK, and the `galaxy_relations` lookup table (21 rows, mirrored from `GALAXY_RELATION_PICKER_OPTIONS`), which `create_connect_invite` validates `p_relation` against.

`[FIXED]` **`connection_grants_person_idx`, as shipped in `20260913160000`, blocked exactly the reconnect flow the plan requires.** It was a plain unique index on `viewer_person_id` with no status predicate. `revoke_connection` does not delete the grant row when it strips a mirror, it sets `status = 'revoked'` and leaves the row (and the now-bare person row) in place, per plan section 3.5. A sender can then regenerate a connect invite targeting that same now-bare person row, since `create_connect_invite`'s merge-target check only requires `linked_user_id is null` and `birth_precision = 'none'`, both true again after a revoke. Accepting that regenerated invite would then collide with the first grant's still-present revoked row on this exact index, even though nothing is actually double-assigned. Narrowed to `unique ... where status <> 'revoked'` in the schema-completion migration above, so a revoked person row's mirror slot frees up while at most one *live* mirror per person row is still enforced. Covered by a round trip test: revoke, then regenerate and re-accept for the same pair, asserting the same `connection_grants` row is reused rather than a unique violation.

`[ADDED]` **`supabase/migrations/20260913180000_constellation_connect_functions.sql`.** All nine functions, `language plpgsql security definer set search_path = public`, explicit `revoke ... from public, anon` / `grant execute ... to authenticated`, matching the existing `delete_own_person` / `purge_own_account_data` pattern:

- `create_connect_invite` / `revoke_connect_invite`: generate and cancel a link. Refuses `child` and `grandchild` outright (the already-confirmed minor-implying classification from `packages/core/src/galaxy-orbit.ts` `resolveGalaxyRelation`, band `children`; not re-derived, read from the shipped schema migration's own column comment and its changelog fragment). Regenerate revokes the prior pending invite for the same merge target before inserting.
- `connect_invite_preview`: the recipient-facing, side-effect-limited-to-lazy-expiry read. Returns only the sender's display name and chosen relation, nothing else about the sender's galaxy.
- `accept_connect_invite`: single accepted use enforced by one `UPDATE ... RETURNING` guarded by `status = 'pending' and expires_at > now()`. Merges into the invite's `person_id` if it still qualifies, else creates a new star. Copies the chart under the recipient's own `house_system`. `share_level = 'chart'` (the client default) leaves birth columns null on the mirror.
- `add_sender_to_constellation`: the separate mutual-add call. Branches on the original invite's `sender_shares_back` (set once, at generate time): pre-authorized gets an immediate active mirror, not pre-authorized gets a bare star and a `pending` reverse grant.
- `set_connection_share_level`, `revoke_connection`, `approve_reverse_grant`: subject-only grant management. Level changes backfill or clear the mirrored birth columns immediately, in the same call, rather than waiting on the next unrelated edit to the subject's own row to trigger the existing sync triggers.
- `acknowledge_connect_accept`: dismisses the sender's acceptance card, mirroring the `relational_transits.push_sent_at` idiom.

`[ADDED]` No entitlement gate anywhere in this file (auth required, a paid plan is not) and no expiry-sweep job (the lazy write-back in `connect_invite_preview` is the only place `status = 'expired'` is ever written), both per the already-locked decisions in the schema migration's changelog fragment.

`[FIXED]` **Multiple `PL/pgSQL` "column reference is ambiguous" bugs caught by local replay, not by inspection.** Four of the nine functions declare an OUT parameter (from `returns table (...)`) whose name is identical to a real column on the table the function reads or writes (`token`, `expires_at`, `person_id`, `sender_shares_back`). An unqualified reference to that name inside the function body, including inside an `UPDATE ... WHERE` clause, an `UPDATE ... RETURNING` list, and an `INSERT ... ON CONFLICT (...)` conflict-target list, is ambiguous between the PL/pgSQL variable and the table column and fails at call time, not at `CREATE FUNCTION` time. Fixed by table-qualifying the column in each spot; the one `ON CONFLICT (person_id)` case (in `add_sender_to_constellation`, whose own OUT parameter is `person_id`) cannot be fixed by qualification, since a conflict-target column list does not accept a table-qualified name, so that one upsert was rewritten as an explicit `if exists (...) then update ... else insert ... end if`. Every one of these was only found by actually executing the round trip against a local replay, never by reading the function bodies.

`[VERIFIED]` **Full round trip against a from-scratch local Postgres replay of every committed migration (no Supabase CLI or Docker available in this environment; a minimal `auth.users` / `auth.uid()` / role stub was layered on top, the same shape as the repo's own `docs/*-retest.sql` scripts already use against the real project).** Generate, preview, accept: grant lands `share_level = 'chart'` by default with no birth columns on the mirror, mirrored chart carries the recipient's own `house_system`. `create_connect_invite('child')` and `('grandchild')` are rejected; `('niece')` is not. Concurrency guard: a second accept of the same consumed token is refused. Merge into an existing bare star, and regenerate for the same merge target, both work. Mutual add exercised on both branches of `sender_shares_back` (immediate mirror vs. bare star plus pending reverse grant, with `approve_reverse_grant` filling the mirror in on approval, subject-only). `set_connection_share_level` backfills or clears immediately. `revoke_connection` strips the mirror and leaves the grant row for later reuse; a full revoke-then-regenerate-then-reaccept cycle reuses the same `connection_grants` row rather than hitting a unique violation. `purge_own_account_data` runs clean for a user who is mid-flow, holding both a pending outstanding invite (as sender) and an active grant (as subject): both are removed, the other side's mirrored chart and birth data are stripped, and that person is left a bare star with their own label and relation intact, no errors.
