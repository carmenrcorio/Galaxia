## Fix the production migration replay defect blocking the main GitHub integration record (branch `cursor/fix-migration-ledger-replay-drift-9d01`), 2026-09-13

**Trigger**: the Supabase GitHub integration's `main` branch record for `eigfvribtntbxyjutsma` had been in `MIGRATIONS_FAILED` since 2026-09-10T00:31:59Z, including but not limited to the four PR #205 migrations that `list_migrations` shows as absent from the production ledger by name.

`[DECISION]` The four PR #205 migrations being absent from the production ledger by name is real, but it is a symptom, not the cause. Every migration from 20260725013000 onward has a ledger row whose `version` does not match its own committed filename timestamp, because it was applied by hand through MCP `apply_migration` (which stamps apply time as `version`, per `ENGINEERING.md` section 16) rather than through the git-triggered integration. A deploy that reconciles pending work by that `version` column, not by name, still sees every one of those committed timestamps as unapplied. Replaying them by version against a database shaped like production's current state reproduces a concrete, reproducible error at the very first one in file order, `20260725040000_person_daily_nudges.sql`: `policy "person_daily_nudges owner all" for table "person_daily_nudges" already exists`. CREATE POLICY has no IF NOT EXISTS form in Postgres, so any migration whose policy statement is not preceded by a matching DROP POLICY IF EXISTS can only ever run once against a given database. Continuing the same replay past that point turns up five more of the same shape: `vela_chat_rate_limit`, `admin_safe_actions_and_support_queue` (the `support_requests` policy), `memorial_milestones`, `relational_transits`, and `push_tokens`. All six policies were confirmed against production's live `pg_policy` before writing the fix, matching each source file's original (pre-#205) definition exactly. This is why the four PR #205 migrations, and now the #217 schema migration behind them, have stayed queued: the integration is stuck retrying a much older, unrelated file, not the newest ones.

`[FIXED]` `supabase/migrations/20260725035959_owner_policy_replay_guard.sql`, a single back-dated file sorted immediately before the earliest offender, drops each of the six named policies first, guarded by `to_regclass` so the drop is a no-op both on a fresh empty database (where the table does not exist yet, and the bare create policy below it is the only run it will ever get) and on a database where the policy has already been removed. Every one of the six is dropped and recreated again later regardless, by `20260726000000_person_daily_nudges_rls_hardening.sql` for the first and by `20260913030100_wrap_auth_uid_in_rls_policies.sql` for all six, so the final shape of each policy is unaffected by whether this file's drop ever finds anything to do. Same pattern already proven safe this session by `20260712200000_rls_auto_enable_definition.sql` and `20260821191400_bootstrap_admin_auth_user.sql`: a new file ahead of the failure, never an edit to an already-applied one.

`[ADDED]` A guard suite in `apps/web/lib/migration-history-replayable.test.ts` pins the six known offenders, asserts the replay guard file sorts ahead of all of them and still contains a matching guarded drop for each, and asserts each offending statement is still bare (unguarded) in its own file, so a future edit that "fixes" one of the already-applied files directly (which `ENGINEERING.md` section 2 forbids) fails this test rather than silently making the guard redundant.

`[FIXED]` Full migration history verified two ways: replayed verbatim from an empty database (54 files, zero errors, extending #220's proof to include #217's schema migration), and replayed as a version-keyed catch-up against a database shaped like production's actual current state (49 files at that state, then all 30 version-unrecorded files in order, ending with the four PR #205 migrations and the #217 schema migration, zero errors). Both replays done with a local PostgreSQL 16 instance and a minimal Supabase platform shim (auth.users, auth.uid(), anon/authenticated/service_role, storage.buckets/objects), since no local Supabase stack exists in-repo.
