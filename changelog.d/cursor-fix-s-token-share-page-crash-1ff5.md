## `/s/[token]` share pages crashing on Vercel after #153 (branch `cursor/fix-s-token-share-page-crash-1ff5`) — 2026-08-31

**Trigger**: launch-blocker report that `/s/[token]` share pages threw a client-side exception in production after #153 (OG cards), even though `/api/quick-share` was writing rows successfully. Confirmed writes for both reported tokens; the failure was on read/render only.

**Root cause (Phase 0)**: production was confirmed on the #153 merge commit (the `/s/[token]/opengraph-image` route existed and rendered a real PNG). Fetching the real deployed page with a headless browser (curl alone hides this — it only shows the streamed SSR shell) showed the visible chart content rendering fine but the async metadata boundary erroring (`data-dgst` marker in the RSC stream, "Application error: a client-side exception has occurred" on hydration) — every `<title>`/`og:*`/`twitter:*` tag was missing. `app/s/[token]/opengraph-image.tsx` read its 5 `.ttf` fonts via a **module-scope top-level `await Promise.all([...readFile...])`**. Next's file-convention metadata resolution imports that same module as a dependency of the sibling `page.tsx` (to read its static `alt`/`size`/`contentType` exports for auto-generated `<meta>` tags) — confirmed by inspecting the compiled `page.js` bundle, which had the entire font-reading module inlined. On Vercel, `page.js`'s own serverless function bundle did not reliably ship those `.ttf` files (output-file-tracing did not detect the transitive `readFile(join(process.cwd(), ...))` call once bundled into another route), so the top-level `await` threw ENOENT there, crashing `generateMetadata` for every request — even though the dedicated `opengraph-image` route's own bundle (which the tracer did detect it for directly) rendered fine standalone.

`[FIXED]` **Fonts load lazily, memoized, inside the `Image` request handler** in `apps/web/app/s/[token]/opengraph-image.tsx` — never at module scope. Confirmed via the compiled bundle that `page.js` no longer references `readFile`/the font loader at all (dead-code-eliminated, since nothing in `page.tsx`'s import graph calls it), so metadata resolution can no longer trip over a missing/slow font read.

`[FIXED]` **A failed font read degrades gracefully instead of crashing the image route.** `loadOgFonts()` is `try`/`catch`-guarded in the handler; on failure it logs and passes `fonts: undefined` (not `[]]`) to `ImageResponse` so `next/og` falls back to Satori's built-in default font — an empty array is truthy and skips that fallback, which crashed the route with "No fonts are loaded." A failed read also isn't cached as a permanent rejection, so a transient miss doesn't wedge a warm container forever.

**Verified**: reproduced end-to-end against a `next build` + standalone-output run with the fonts directory deleted (simulating the exact missing-bundle-asset failure) — before the fix, the page's metadata boundary crashed (error digest in the RSC stream) and the image route threw "No fonts are loaded."; after the fix, the page renders with full `<title>`/OG/Twitter metadata and the image route serves a valid fallback-font PNG, in both the fonts-present and fonts-deleted cases. A forged/missing token still renders the graceful not-found page (unchanged `notFound()` in `page.tsx`). `apps/web` vitest (`lib/og-share-route-wiring.test.ts` updated to assert lazy loading + the `try`/`catch` fallback instead of the old module-scope pattern; `lib/og-card.test.ts` unchanged) and `pnpm typecheck` pass repo-wide; full `pnpm test` (462 web + 132 astro + 27 vela + 28 mobile tests) green.

**Not touched**: `outputFileTracingIncludes` was tried as an alternative/defense-in-depth fix but is not usable here — Next 15.5.23 mangles backslash-escaped `\[token\]` in the *value* glob (it unconditionally replaces `\` with `/` when normalizing includes), so a directory literally named `[token]` cannot be targeted that way. The lazy-load fix removes the need for it. No safety/strip logic in `lib/og-card.ts` or `lib/quick-share.ts` was touched.
