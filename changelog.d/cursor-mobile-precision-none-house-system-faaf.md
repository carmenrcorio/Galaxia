## Mobile precision parity + saved house system (branch `cursor/mobile-precision-none-house-system-faaf`) — 2026-09-13

**Trigger**: two pre-existing mobile/web parity gaps surfaced during the constellation-connect plan review. Mobile could not save a person without birth data, and every chart saved from the phone claimed Placidus regardless of the owner's stored preference. Both would have silently degraded that upcoming feature, and both are real bugs on their own.

`[FIXED]` **Mobile charts now use `profiles.house_system` instead of a hardcoded `"placidus"`.** `apps/mobile/app/(app)/onboarding.tsx` was the only `computeNatalChart` call site in the mobile app and it passed the literal `houseSystem: "placidus"`, so a user who had chosen Whole Sign or Equal House in web Settings got a Placidus chart whenever the person was added from the phone. Mobile now reads the preference through a new `apps/mobile/src/lib/house-system.ts`, a mirror of `apps/web/lib/house-system.ts`: it reuses the shared `isHouseSystem` predicate and falls back to Placidus only for a profile with no valid stored value, never over an existing one. `charts.house_system` still records what the engine actually computed (polar fallback included), so nothing here weakens ENGINEERING §12. The same write also switched `engine_version: 2` to the exported `CHART_ENGINE_VERSION`, the same drift class as the hardcoded system. The preference remains web-settable only; mobile has no house-system picker yet.

`[ADDED]` **Mobile can save a person with no birth data (`birth_precision: "none"`), matching web's four-tier precision model.** Mobile already had `exact`, `date`, and `year`; the missing tier was the bare one. `BirthFormInput.precision` has always been `FormPrecision = Precision | "none"`, but mobile's tier array narrowed to `Precision`, so the UI could never produce it, and its write path called `buildBirthInput` unconditionally, which throws on `"none"` by design rather than synthesizing a date. Mobile's `BirthFields` now takes an `allowNone` prop and the write path branches first, inserting the row built by the new `apps/mobile/src/lib/deferred-person-row.ts` with every birth column null and no `charts` row at all. Web parity is deliberate down to where the tier appears: only the add-person form passes `allowNone`, so your own profile still starts from real birth data, exactly as `/welcome` does.

`[FIXED]` **Mobile person profile renders someone who has no chart yet.** `apps/mobile/app/(app)/profile/[personId].tsx` fetched the chart with `.single()` and treated a missing row as a hard failure ("Unable to load chart."), which would have made every deferred person unopenable on the phone. It now uses `maybeSingle()` and renders a "no birth data yet" state alongside the private notes, the same shape web's person page has had. Mobile home already tolerated a chart-less person.

New copy for the deferred tier (the tier label and description, the save confirmation, and the empty-chart card) is tagged `FOUNDER-REVIEW`; the tier label and description are web's existing "Add birth data later" strings verbatim so the two surfaces read the same.

**Verified**: `pnpm --filter @galaxia/mobile typecheck`, `test`, and `lint` clean, plus `pnpm typecheck` and `pnpm test` across the monorepo. New `apps/mobile/src/lib/mobile-precision-house-system-parity.test.ts` (10 tests) covers the preference read and its Placidus-only fallback, proves the preference actually moves the cusps, asserts the deferred row leaves every birth column null and keeps the manual minor flag, and guards the wiring on both screens.
