## Make the committed migration history applicable to an empty database (branch `cursor/replayable-migration-history-9087`), 2026-09-13

**Trigger**: the `Supabase Preview` check fails on every pull request that touches `supabase/migrations`, and has since at least #205. It builds a brand new project, applies `supabase/migrations/*.sql` from zero, and aborts. The check is path-filtered, so #206 through #213 all skipped it and nobody saw the red. Found while opening #217 and #218, which both tripped it.

`[FIXED]` **`public.rls_auto_enable()` now has a definition in the repo**, added as `20260712200000_rls_auto_enable_definition.sql`. The next migration, `20260712210000_rls_cross_user_hardening.sql`, has always ended with `revoke execute on function public.rls_auto_enable() from public, anon, authenticated`, and that statement has always worked against production because the function is genuinely there, created out of band before this history began. It could never work against a database built only from this repo: `ERROR: function public.rls_auto_enable() does not exist (SQLSTATE 42883)`. The function is the backstop that enables RLS on every newly created public table, and the `ensure_rls` event trigger that calls it is committed alongside.

`[FIXED]` **The first-admin bootstrap no longer requires an account that a fresh project cannot have**, added as `20260821191400_bootstrap_admin_auth_user.sql`. `20260821191500_admin_role_foundation.sql` seeds the founder into `admin_users`, whose `owner_id` references `auth.users(id)`, and is right to key off a stable id rather than a mutable email. The unstated precondition was that the account already exists, which is true in production and false in an empty project: `ERROR: insert or update on table "admin_users" violates foreign key constraint "admin_users_owner_id_fkey"`.

`[DECISION]` **Both fixes are back-dated files rather than edits to the migrations that need them.** A file dated after the failing statement cannot repair it, because the failure happens first. The alternative was editing two already-applied migrations, which `ENGINEERING.md` section 2 forbids, so the fix goes in ahead of each one instead: `20260712200000` sits between `20260712190000` and the hardening migration, and `20260821191400` sits one minute before the foundation migration. Chosen over relaxing or path-excluding the `Supabase Preview` check, because a history that cannot be replayed is a real defect and the check was correctly reporting it.

`[DECISION]` **Both files are no-ops against production, and the guards are written so that is provable rather than hoped for.** The `rls_auto_enable()` body is reproduced verbatim from production `pg_proc`, confirmed by `md5(pg_get_functiondef(oid))` matching on both sides (`6998ea6b4c2480f5d2e34b5dcf3f8d36`) across different major versions, local 16.15 against production 17.6, so the `CREATE OR REPLACE` resolves to the definition already installed. The admin bootstrap inserts only when `auth.users` is *entirely empty*, not merely when the founder id is missing: an empty auth table means a disposable project, whereas the narrower guard would manufacture a founder row in a live database that had lost one. Production held 17 accounts when this was written, so the insert cannot fire there.

`[ADDED]` **`apps/web/lib/migration-history-replayable.test.ts`**, 13 guards. The generalizing one holds every function the history revokes execute on, and every function it attaches a trigger to, against the set of functions the history creates; run against the tree before this branch it names `20260712210000_rls_cross_user_hardening.sql: rls_auto_enable()` exactly. The rest pin both fixes, including that the admin seed keeps the empty-table guard and inserts nothing but the id, so the row cannot be authenticated as.

`[NOTE]` **The `Vercel` failure on migration pull requests was the same defect one step downstream.** Migration branches get two deployments where ordinary ones get a single successful deployment: #210 and #211 have one each, #205, #217, and #218 have one success plus one failure. The second is the Supabase integration redeploying against a preview branch that never came up.

`[NOTE]` **Verified by replaying the history into throwaway PostgreSQL 16 databases two ways.** From empty, with no ad-hoc production objects and no accounts, all 52 migrations now apply with no errors where the tree before this branch stopped at the 15th statement of the 21st file. Against a production-shaped database that already has the function and the founder, both new files change nothing: `auth.users` stays at one row. `#217`'s 66 assertions also pass on the from-scratch database, so that migration is now verified from zero rather than only against a shim.

`[OPEN]` **A database with at least one account but no founder row still fails `20260821191500`.** Deliberate, and documented in the file: such a database is not a fresh project, and silently injecting an admin into it is the outcome most worth avoiding. Revisit only if a real restore-from-backup workflow needs it.
