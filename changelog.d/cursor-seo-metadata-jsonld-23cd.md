## Unique per-route metadata + JSON-LD structured data (branch `cursor/seo-metadata-jsonld-23cd`) — 2026-09-09

**Trigger**: `/download`, `/login`, `/signup`, `/chart`, and `/chart/compare` had no page-level metadata, so all five silently inherited the root layout's generic title ("Galaxia") and description ("Astrologically-driven relationship intelligence") — five distinct URLs unfurling and ranking with identical, non-descriptive copy. Separately, the site had no structured data (`application/ld+json`) anywhere, leaving search engines to guess at what Galaxia is and what a blog post's publish/author info is.

`[ADDED]` **`apps/web/components/seo/json-ld.tsx`** — a small server-only `<JsonLd data={...}>` component that renders a single `<script type="application/ld+json">` tag via `dangerouslySetInnerHTML` (JSON-LD must be raw JSON, not escaped). It has no `"use client"` directive and takes no hooks, so it — and anything that renders it — must stay a Server Component for the tag to land in the initial server-rendered HTML rather than being injected after hydration.

`[ADDED]` **`/download`, `/login`, `/signup`** each now export their own `metadata` (title, description, and matching `openGraph`/`twitter` — Next merges metadata per top-level key, not deep-per-field, so each restates the full object rather than partially overriding the layout default) with copy specific to what that page actually does.

`[ADDED]` **`app/chart/layout.tsx`** and **`app/chart/compare/layout.tsx`** — `app/chart/page.tsx` and `app/chart/compare/page.tsx` are both `"use client"` (they drive the quick-chart/quick-compare forms with hooks) and so cannot export `metadata` themselves; these new server-component layout siblings carry the per-route metadata instead. `/chart`'s copy ("Free Birth Chart Calculator") matches what the page actually offers — a free, real computed natal chart, not a sun-sign guess — per this being the strongest free-tool landing page for search traffic. `/chart/compare` gets its own synastry-specific copy, which fully overrides (not merges with) the parent `/chart` layout's metadata for that subtree.

`[ADDED]` **Homepage `SoftwareApplication`/`Organization` JSON-LD** (`app/page.tsx`) — a single static JSON-LD object (schema.org `SoftwareApplication`, free `Offer`, `Organization` publisher with a `ContactPoint`) rendered via `<JsonLd>` on `/` only. `HomePage` was already a plain Server Component, so this required no other changes to keep it server-rendered.

`[ADDED]` **Per-post `Article` JSON-LD** (`app/[slug]/page.tsx`) — every published blog post now renders an `Article` JSON-LD block built from the same `BlogPost` row `generateMetadata` already reads (`title`, `publishedAt`) plus a new `updatedAt` field. Added `updated_at` to `POST_FIELDS`/`PostRow`/`toBlogPost` in `lib/blog.ts` (the column already existed on `public.posts`, just wasn't selected) so `dateModified` reflects the real last-write timestamp instead of falling back to `publishedAt` on every post.

`[OPEN]` Skipped `FAQPage` JSON-LD for `/synastry-chart-meaning`'s "What a chart cannot tell you" section — its content is four declarative statements ("A synastry chart cannot tell you whether to stay," "It cannot tell you who is at fault," …), not phrased as explicit questions and answers. Forcing an FAQ schema onto non-Q&A prose risks a Search Console structured-data mismatch penalty; revisit if that section is ever rewritten in actual Q&A form.

Verified: `pnpm --filter @galaxia/web typecheck` and `pnpm --filter @galaxia/web build` both pass; `next build && next start` then `curl`ing the raw (pre-hydration) HTML confirms unique `<title>`/`<meta name="description">` on all five routes and a server-rendered `<script type="application/ld+json">` on `/` (`SoftwareApplication`) and `/synastry-chart-meaning` (`Article`, with real Supabase-backed `headline`/`datePublished`/`dateModified`). Full `pnpm test` (462 web + 132 astro + 28 mobile + 27 vela tests) still passes.
