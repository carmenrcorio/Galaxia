## vela-chat rate limit: atomic per-user admission check (branch `cursor/vela-chat-rate-limit-migration-05f0`) — 2026-08-19

**Trigger**: security audit found no rate limit on `vela-chat` — any authenticated user, including a zero-payment trial account, could script unlimited sequential or concurrent requests with no backstop on real Anthropic spend. The only finding that mapped to unbounded real-money loss.

`[ADDED]` **`vela_rate_limits` table + `check_and_increment_vela_rate` RPC** (`supabase/migrations/20260725050000_vela_chat_rate_limit.sql`) — one counter row per user, `SECURITY DEFINER`, bound to `auth.uid()` internally (mirrors `delete_own_person` / `purge_own_account_data`). Check-and-record is a single locking `UPDATE`, not select-then-write, so it holds under concurrent callers via Postgres row-level locking + `EvalPlanQual` re-evaluation. `execute` revoked from `anon`/`public`, granted to `authenticated` only. Owner-scoped read-only RLS; no client write policy — all writes go through the RPC.

`[ADDED]` **Admission check wired into `vela-chat/index.ts`**, immediately after the entitlement 403 return and before request-body parsing, so it gates everything past the entitlement gate (including `action === "consent"`) and a throttled request creates zero `threads`/`messages` rows and spends zero Anthropic budget. Tier resolves from the same two profile fields `profileAllowsAccess` already reads (`comped`, `subscription_status`) — no second profile read, no new access decision. Does not touch the entitlement gate, `hasAccess`, `isMinorForSafety`, mode discrimination, or any interpretation copy. No concurrency semaphore in this version — a tight per-window count is the first cut.

`[FIXED]` **Comped tier misclassification** — `comped` and `subscription_status` are independent fields, and nothing ever changes `subscription_status` when `comped` is set, so a comped account resting at `subscription_status = "trialing"` (the founder's own account's actual live shape) was classified as trial and capped at 5 instead of 20. `isTrial` now excludes `comped` explicitly: `!profile?.comped && profile?.subscription_status === "trialing"`. Found live during verification: fired a scripted concurrent burst against the founder's real account (via an admin-generated, single-use magiclink session, no password touched, signed out after) and observed the wrong cap before the fix, then exactly 20 admitted / 5 denied after.

`[DECISION]` **FOUNDER-REVIEW placeholders, not finalized**: paid cap 20/600s, trial cap 5/600s, RPC-error fail mode (503, fail-closed — a transient DB blip refuses rather than silently dropping the cap), and the 429/503 response copy (`RATE_LIMIT_COPY`, `RATE_LIMIT_503_COPY` in `index.ts`). Client already renders `body.error` on both web (`apps/web/app/app/vela/page.tsx`) and mobile (`apps/mobile/app/(app)/vela.tsx`) with no new UI plumbing needed.

**After merge**: this is a Postgres migration + a Supabase Edge Function — **NEITHER SHIPS ON MERGE**. Requires `supabase db push` and `supabase functions deploy vela-chat --project-ref eigfvribtntbxyjutsma` as explicit follow-up steps.
