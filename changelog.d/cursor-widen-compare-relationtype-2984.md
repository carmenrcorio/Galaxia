## Widen persisted compare-share relationType to the full RelationType union (branch `cursor/widen-compare-relationtype-2984`) — 2026-08-26

**Trigger**: `/app/compare` narrowed its full 5-way `RelationType` picker down to `romantic`/`platonic` before the `/api/quick-share` POST, so a compare share could never render a real relationship summary (siblings, friends, parent-child, ancestor all flattened to the single word "platonic"). Phase 0 diagnosis confirmed the fix is a small, compiler-guided persist-layer change with no DB migration and no birth-PII strip change.

`[CHANGED]` **`CompareSharePayload.relationType`** widens from `"romantic" | "platonic"` to the full `RelationType` union (`packages/astro`'s `partners`, `siblings`, `friends`, `parent-child`, `ancestor`, `romantic`, `platonic`). `validateQuickSharePersistBody`'s allow-list is now a membership check driven by the exported `COMPARE_RELATION_TYPES` plus the two binary-only values, not hand-copied literals, so a future 8th `RelationType` needs no edit here. The persist-time minor+romantic structural guarantee is unchanged: it already called the canonical `isRomanticRelation()` generically.

`[CHANGED]` **`/app/compare`'s `createShareUrl()`** stops collapsing the picker's real `relationType` to a binary before persisting; it now sends the real value and only snaps to `platonic` when a minor is in the pairing and the chosen type is romantic-family (same safety behavior as before, now correct for `partners` too, not only `romantic`).

`[FIXED]` **The one remaining `=== "romantic"` string check** in `whatTheyNeed()`'s `isPartnerLens` (`packages/astro/src/compare-guidance.ts`) and in `FlowsAndCatchesSection`'s `introFor()` (`apps/web/components/flows-and-catches-section.tsx`) now route through the canonical `isRomanticRelation()` instead of re-deriving the romantic-family set inline. A repo-wide grep confirms zero `=== "romantic"` / `!== "romantic"` string comparisons remain in the compare/share render or persist paths.

`[ADDED]` **Completeness test** (`packages/astro/test/relation-type-completeness.test.ts`): for every `RelationType` not in `ROMANTIC_RELATION_TYPES`, `whatTheyNeed()` must never surface the attraction-framed Venus/warmth-score line or the partner high-flow line. This converts the hand-maintained `ROMANTIC_RELATION_TYPES` array into a CI-guarded invariant, so a future attraction-framed relationship type that is forgotten from the array fails the build instead of leaking onto a public share.

`[ADDED]` Backward-compat coverage in `apps/web/lib/quick-share.test.ts`: existing binary rows (`romantic`/`platonic`) still validate and render unchanged; the full union (including `partners` + minor) is exercised through both `validateQuickSharePersistBody` and the `effectiveCompareFraming` render backstop. No DB migration and no backfill were needed: `relationType` lives inside the schemaless `payload` jsonb column, and old binary values remain valid members of the widened type.
