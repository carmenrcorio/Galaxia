## Nudge delivery Phase B1: server compute job + tz-aware `ownerLocalDate` (branch `feat/server-nudge-job`) — 2026-08-21

**Trigger**: `person_daily_nudges` rows were only ever written client-side, on app open — a lapsed user who never opens the app never gets a row for that day. This phase adds the server-side job that computes and writes rows independent of app opens, using `profiles.timezone` (Phase A) to get the owner's real calendar day on a UTC-runtime server. NO email, NO consent, NO sending in this phase — compute and write only. Consent, templates, and unsubscribe are Phase B2.

**Phase 0 — confirmed before writing code:** all three existing callers of `ownerLocalDate`/`whenUTCForOwnerLocalDate` (web home, web person page, mobile home) run in the browser/device, so "runtime tz" was correct by accident. Everything the server job needs (`people`, `charts.data`, `profiles.timezone`, recent `person_daily_nudges` for the 45-day novelty window) is a plain service-role-readable table; `peopleForTodaySky` and `isMinorForSafety` are pure, already proven importable outside a browser (`person-daily-nudges-concurrency.test.ts` does this today). No client-only blocker found.

`[ADDED]` **Optional `timezone?: string | null` param on `ownerLocalDate` and `whenUTCForOwnerLocalDate`** (`packages/astro/src/transit-nudge/dates.ts`). Omitted, `null`, or an unparseable IANA string: byte-identical to the pre-B1 runtime-tz path (verified — `transit-nudge-dates.test.ts` asserts the omitted-tz output against a frozen copy of the pre-B1 implementation). A valid IANA zone: `ownerLocalDate` derives the day via `Intl.DateTimeFormat("en-CA", { timeZone, ... })`; `whenUTCForOwnerLocalDate` computes the DST-correct UTC instant for that zone's local noon via a guess-then-correct offset lookup (`Intl.DateTimeFormat` with `timeZoneName: "longOffset"`) — not noon-in-the-runtime's-tz, which would be wrong on a UTC server. No new dependency; Node's built-in full-ICU `Intl` already handles this correctly (verified live: `America/Los_Angeles` resolves the correct PST/PDT offset and calendar day across a DST boundary).

`[ADDED]` **`apps/web/app/api/cron/nudge-compute/route.ts`** — the server compute job, mirroring `../trial-emails/route.ts`'s shape exactly: `CRON_SECRET` bearer auth (unset → 503, wrong/missing header → 401), service-role client with `persistSession: false`, Node runtime (no `edge` export). For every `profiles` row with a non-null `timezone`: loads that owner's `people` + `charts.data` + today's existing `person_daily_nudges` + the 45-day pass-id novelty window, applies `peopleForTodaySky` and `isMinorForSafety` **imported unmodified** from `@galaxia/core` (never re-derived inline), computes today via the new tz-aware `ownerLocalDate`/`whenUTCForOwnerLocalDate` using that owner's stored `timezone`, runs `planDailyNudgeWrites`/`buildPersonDailyNudge` unmodified, and upserts with `{ onConflict: "person_id,date", ignoreDuplicates: true }` — identical conflict semantics to every client caller, so the server job and a client on-open write racing for the same row leave exactly one, first-write-wins. **No email, no `Resend`, no `sendEmail` — this route only ever calls `.from(...)` on `profiles`, `people`, `charts`, and `person_daily_nudges`** (asserted in `nudge-compute-route-wiring.test.ts`).

`[DECISION]` **Null `profiles.timezone` → skip, never fabricate.** A user who hasn't loaded the app since Phase A shipped is skipped entirely this run (filtered at the query level via `.not("timezone", "is", null)`, plus a defensive in-loop guard) — they get their row the normal way next time they open the app, same as today. Falling back to UTC would violate `ENGINEERING.md` §12 (never fabricate a value we have no basis for) and would freeze a possibly-wrong day forever, since `buildPersonDailyNudge`'s copy is never recomputed once written.

`[OPEN]` **Stale-tz-vs-traveling-user divergence, inherited from Phase A, deliberately not fixed here.** Phase A's `shouldBackfillTimezone` never re-writes an already-stored `profiles.timezone`, so a traveling user's live browser tz can drift from their stored value. If it does, the client and this server job can compute *different* calendar days for the same person — not a primary-key collision (`(person_id, date)` differs, so no upsert conflict), but two valid-looking rows for adjacent days, a softer duplicate-content risk. Founder decision locked this as out of scope for B1 (do not re-open the timezone source); re-syncing a changed tz is future/Phase-B2+ work.

`[VERIFIED]`:
- **Tz-correctness (non-UTC, live project)**: a real throwaway account with `profiles.timezone = "America/Los_Angeles"` got its `person_daily_nudges` row dated the true LA-local calendar day (`scripts/verify-nudge-compute-job.mjs`, run against the live Supabase project through the actual `CRON_SECRET`-gated route on a running `apps/web` dev server) — confirmed against an independently-computed `Intl`-based reference date, not the job's own output.
- **Safety reproduction (live project)**: in the same run, a passed person in that account's people got no row (`peopleForTodaySky`), and a person with `is_minor: false` but a birth date computed as under 18 got a row with `minor_safe: true` (`isMinorForSafety`'s age computation, not just the raw flag) — proving the server call site reproduces the client's safety filtering exactly.
- **Idempotency, both orders (live project)**: server-job-write then simulated-client-write, and simulated-client-write then server-job-rerun, for the same `(person_id, date)` each left exactly one row with the first writer's content frozen.
- **Null-tz skip (live project)**: a second throwaway account with no stored timezone got zero rows written, at any date — never a fabricated UTC day.
- **Regression guard**: `packages/astro/test/transit-nudge-dates.test.ts` asserts omitted/`null`/invalid-tz output of both functions equals the pre-B1 reference implementation, so the three existing client callers (web home, web person page, mobile home — none of which pass a third argument) are unaffected.
- **Auth fail-closed (live, manual)**: unset `CRON_SECRET` → 503; missing/wrong bearer → 401; correct bearer → 200 — verified with `curl` against a running dev server, both with and without `CRON_SECRET` set.
- `pnpm typecheck` passes across all six packages. Full `@galaxia/astro`, `@galaxia/core`, `@galaxia/web`, `@galaxia/vela` test suites pass (120 / 155 / 199 / 27 tests respectively); `@galaxia/mobile` typechecks.
- Scheduling remains genuinely out-of-band: no `vercel.json` was added (`ENGINEERING.md` §2 — there is deliberately none in this repo). Point a Vercel dashboard cron job or Supabase `pg_cron` (`net.http_post`) at this route; neither is configured yet in this phase, by design — B1 is compute-and-write only, not scheduled sending.
