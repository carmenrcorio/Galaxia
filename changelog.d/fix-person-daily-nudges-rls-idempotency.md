## `person_daily_nudges` audit close-out: RLS ownership gap, idempotency, VERIFY proofs (branch `fix/person-daily-nudges-rls-idempotency`) — 2026-08-20

**Trigger**: A close-out audit of the shipped transit nudge engine (PR #118, live since 2026-07-25) found the table's RLS policy landed after the 2026-07-12 cross-user hardening pass and missed the same "referenced people must be owned by the writer" pattern, the three upsert call sites used update-on-conflict instead of the spec's "first write wins, frozen forever", and the spec's end-to-end guarantees had unit coverage but no real proof.

`[FIXED]` **`person_daily_nudges` RLS ownership gap — an INTEGRITY fix, not a read-leak fix.** `owner_id = auth.uid()` was already correctly enforced, so another owner could never `SELECT` a row they don't own — read isolation was never broken. The gap: a caller authenticated as owner A could `INSERT`/`UPDATE` a row whose `person_id` pointed at a person owned by B (B still couldn't read it — `owner_id` stayed A's). Tightened both `USING` and `WITH CHECK` on `"person_daily_nudges owner all"` to also require `EXISTS (SELECT 1 FROM people p WHERE p.id = person_daily_nudges.person_id AND p.owner_id = auth.uid())`, matching the FIX 4 pattern in `20260712210000_rls_cross_user_hardening.sql`. Additive migration: `supabase/migrations/20260726000000_person_daily_nudges_rls_hardening.sql` (`drop policy` + `create policy`, table untouched). **Live-verified** (project `eigfvribtntbxyjutsma`): before the migration, a real two-account script proved account A could write a nudge row referencing account B's person; after, the identical attempt is rejected with "new row violates row-level security policy", and a legitimate same-owner write/read still succeeds. Read isolation (account B reading account A's row) was confirmed blocked both before and after, so the fix does not change severity of anything already-safe.

`[FIXED]` **Idempotency: "first write wins, frozen forever," for real.** All three call sites (`apps/web/app/app/page.tsx`, `apps/web/app/app/person/[id]/page.tsx`, `apps/mobile/app/(app)/home.tsx`) upserted `person_daily_nudges` with the PostgREST default (update-on-conflict) on `onConflict: "person_id,date"`, which would let a genuine race between two writers silently overwrite the first writer's frozen row. Switched all three to `{ onConflict: "person_id,date", ignoreDuplicates: true }` (insert-or-do-nothing) — byte-identical across web and mobile, no drift. Confirmed safe: `planDailyNudgeWrites` (`packages/astro/src/transit-nudge/plan.ts`) only ever builds rows for people missing from `existingRows`, so in the non-race path the default merge behavior was already never exercised — nothing downstream relies on same-day overwrite/recompute.

`[ADDED]` **VERIFY proofs for the spec's end-to-end claims** (previously unit-tested pieces, but not proven together, end to end):
- `packages/astro/test/transit-nudge-verify.test.ts` — a real Saturn-square-natal-Uranus transit, scanned across a real ~2.5 year range through the actual `buildPersonDailyNudge` pipeline, produces exactly 3 distinct `pass_id`s (direct, retrograde re-pass, direct) clustered at the real exact passes, and is silent (zero selections) across the >5 month gap between them; and the same person/date computed in `exact` vs `date_sign` mode side by side, where `date_sign` never targets natal Moon and never writes `orb_deg` while `exact` does, holding across a 400-day scan.
